# SnapBack

[English](README.md) · [Русский](README.ru.md) · **简体中文**

**无需重启，让 Windows 会话回到刚开机时的状态。**

刚登录时，Windows 处于相对干净的状态：系统进程、启动应用，仅此而已。几个小时后，浏览器、
Discord、Telegram、IDE、Python 和 Node.js 进程、WSL、Docker、各种启动器和后台助手程序都堆积了起来。
SnapBack 会记住你想要的状态（**基线**，baseline，或者多个命名的**配置文件**，例如“干净”“工作”
“游戏”），显示会话已经偏离了多远、真正占用内存的是什么，并以**礼貌的方式**让会话回到该状态——
像你点击 ✕ 一样关闭多余的应用，应用可以保存你的工作或先询问你。

SnapBack **不是**“内存清理器”或“电脑加速器”。它的主要任务是在你同意后关闭基线之后启动的应用。
另有一个明确分开的可选功能*深度内存清理*，用于你明确想要丢弃 Windows 文件缓存的少数情况。

---

## 工作原理

1. **基线。** 点击“将当前状态设为基线”（或在登录几分钟、启动应用全部启动完毕后让 SnapBack
   自动创建）。基线记录的是**应用**，而不仅仅是进程 ID。
2. **比较。** SnapBack 把进程归组为应用（Chrome 的 30 个 `chrome.exe` 是一个应用；VS Code 及其
   辅助进程是一个应用），并与基线进行比较。基线中的应用即使重启或更新后仍属于基线；基线应用新
   产生的子进程绝不会成为关闭它的理由。
3. **查看。** 你可以看到基线之后新增的内容——图标、内存、进程数和风险评估，并可按任意列排序和
   搜索：

   | 应用                  | 内存   | 评估               |
   |-----------------------|-------:|--------------------|
   | Discord               | 650 MB | 安全               |
   | Visual Studio Code    | 1.4 GB | 可能有未保存的数据 |
   | python.exe — train.py | 740 MB | 需人工确认         |
   | Google Chrome         | 3.2 GB | 基线中已存在       |

   只有标记为**“安全”**的应用会被预先选中。你可以取消任何一项，或把应用加入“始终保留”列表。
4. **预览。** 在执行任何操作之前，预览会列出 SnapBack 将执行的每一个步骤。**试运行**会在不做任何
   更改的情况下，对当前系统重新检查每个步骤。
5. **礼貌关闭。** 所选应用会以正常方式收到关闭请求，并有时间保存或询问你。不会强制结束任何程序。
6. **由你决定。** 未关闭的应用（例如正在询问“是否保存更改？”）会单独列出。你可以切换到这些应用
   后点击“重新检查”，或单独、明确地选择强制结束特定应用。
7. **之前 → 之后。** 结果会显示操作前后的应用数、进程数、已用内存、可用内存和缓存，以及关闭的应用
   所释放的内存。

## 仪表板：会话偏移和预期效果

窗口顶部显示的是你做决定所需的信息，而不是一个完整的系统监视器：

```text
配置文件：干净             会话时长：10 小时 21 分钟
会话偏移      正在运行的应用   已用内存        基线之后新增   预期效果
高            31               18.4 GB         12 个应用      高
+12 · +87 ·   286 个进程       可用 13.2 GB    7.1 GB         约 7.1 GB，来自
+7.1 GB                                                       9 个所选应用
```

- **会话偏移**（*低 / 中 / 高*）——会话偏离配置文件的程度。0 到 100 的得分由四个各有上限的部分
  相加：新增应用（每个 4 分，最多 40 分）、它们占用的内存相对于物理内存总量的比例（每 1% 计 2 分，
  最多 40 分）、额外的进程（每 8 个计 1 分，最多 10 分）以及基线时长（满一天后最多 10 分，仅在有
  新增内容时计入）。低于 20 为低，低于 50 为中，更高则为高。缓存内存从不计入。
- **预期效果**——在关闭任何内容*之前*做出的估计：将被关闭的应用的私有内存与物理内存总量之比
  （达到 10% 及以上为高，达到 4% 及以上——或者应用数达到 8 个及以上——为中）。它的工具提示和预览
  会把*已用内存*拆分为新增应用、配置文件中的应用和系统及其他，并单独显示缓存，因为缓存本来就是
  可用的：

  ```text
  已用内存：23.4 GB
    新增应用：7.8 GB
    配置文件中的应用：4.9 GB
    系统及其他：10.7 GB
  缓存 / 待机：7.0 GB（已可用，不算占用）
  预计可回收：约 7.8 GB      预期效果：高
  ```

  如果大部分内存并非由基线之后新增的应用占用，SnapBack 会如实说明——而且它从不承诺一个确切的
  数字：共享内存、拒绝关闭的应用以及 Windows 的缓存都会使实际结果有所不同。

## 配置文件

除了单一的基线，你还可以保存多个配置文件——例如“干净”“工作”“游戏”“直播”——每个配置文件都有
自己应保持运行的应用列表。在**“配置文件”**中，你可以从当前状态创建配置文件、重命名、从当前状态
更新、移除或添加单个应用、删除配置文件，以及选择默认配置文件。主窗口中的配置文件选择器决定会话
与哪个配置文件进行比较；选择配置文件不会关闭任何内容。

于是“准备玩游戏”就很简单：选择“游戏”（Steam、Discord、GPU 工具、游戏启动器），然后点击
**返回到“游戏”…**——常规预览会建议关闭 IDE、多余的浏览器和工作应用。配置文件还可以建议停止
WSL 和 Docker（见下文）；每次都需要你确认。没有任何硬编码的配置文件：建议的名称只是可以编辑的
建议。

早期版本中的单个 `baseline.json` 会自动变为配置文件“干净”。

## 规则：始终保留、始终关闭、每次询问

在列表中右键单击应用（或使用“设置 → 规则”）：

- **始终保留**——在任何配置文件中都不会被建议关闭。
- **始终关闭**——每次返回配置文件时都会被预先选中，即使在捕获该配置文件时它正在运行。
- **每次询问**——会被建议关闭，但绝不会被预先选中。

规则只决定建议哪些应用以及勾选哪些应用。它们绝不会改变保护状态，绝不会跳过预览、礼貌关闭或实时
安全检查，“始终关闭”也绝不会强制结束任何程序。

## 内存随时间变化

SnapBack 运行期间，最多每 10 分钟记录一次每个正在运行的应用的已提交内存（每次分析时顺便记录一个
样本；每个应用最多 96 个样本、最多 64 个应用，仅保存在内存中）。**内存**窗口会显示内存持续增长的
应用：

```text
Discord              内存异常增长
9 小时内 420 MB → 1.4 GB
10:00 420 MB · 13:00 610 MB · 16:00 940 MB · 19:00 1.4 GB
```

“内存异常增长”的含义是：在至少两小时内，增长至少 +500 MB 且达到 ×1.5，并且大多数时间点都在上升。
SnapBack 从不称之为泄漏——缓存和更多的工作（标签页、文档）也会使内存增长；重新启动应用即可释放
这些内存。

## WSL 和 Docker

WSL（`vmmemWSL`/`vmmem`、`wslhost`、`wslservice`）和 Docker Desktop（`Docker Desktop.exe`、
`com.docker.*`、`vpnkit`）会被识别出来，并且**绝不会作为普通应用被关闭**——它们是受保护的。
它们运行时，仪表板会显示它们的内存以及各自的停止操作：

- **关闭 WSL…** 运行 `wsl --shutdown`。
- **停止 Docker…** 运行 `docker desktop stop`（需要 Docker Desktop 4.37 或更高版本；更早的版本会
  报告为不支持——请通过 Docker Desktop 的托盘图标退出它）。

停止之前，SnapBack 会列出将要停止的内容——正在运行的发行版（`wsl --list --running`）或正在运行的
容器（`docker ps`）——并警告其中的 Linux 服务、容器以及未保存的工作也会一并停止。在真正运行命令
之前，它会再检查一次；如果在此期间启动了新内容，就不会停止任何内容，并会再次询问你。SnapBack
绝不会结束 `vmmem` 或 Docker 进程，而且它只在环境已经运行时才执行这些只读命令，因此它自己绝不会
启动 WSL 或 Docker。

## 内存：哪些是真正占用的，哪些只是缓存

Windows 会把最近使用的数据作为**备用缓存**（standby）保留在内存中。这些缓存算作**可用**内存：
任何需要内存的应用都能立即从 Windows 获得它。“已缓存”数值高是正常且健康的，“空闲”内存只是未被
使用的内存。

因此 SnapBack 会如实展示两方面：

- **已用内存**和**可用**——应用和系统真正占用的内存，以及可用的内存。
- **已缓存（备用 + 已修改）**——可重新利用的缓存。
- **关闭应用释放的内存**——已退出应用的私有内存。这才是“返回基线”的真实效果。

**内存**窗口会用通俗的语言解释当前情况。可用内存充足时，它会直接说明并且不建议任何清理；内存不足
时，它会说明真正有帮助的是关闭应用。

### 深度内存清理（可选，高级）

内存窗口中的一个单独操作（也可以从“返回基线”的结果中打开）。它**永远不会自动运行**，也**永远不是
“返回基线”的一部分**。

- **机制：** 使用 `NtSetSystemInformation(SystemMemoryListInformation, …)` 的备用列表清除命令——
  与 Sysinternals RAMMap 的 *Empty Standby List* 相同。两种模式：*全部备用缓存*
  （`MemoryPurgeStandbyList`）或*仅低优先级备用缓存*（`MemoryPurgeLowPriorityStandbyList`）。
- **清除：** 备用页（当前未使用的缓存数据）。它们会立即变为空闲内存。
- **绝不触及：** 应用正在使用的内存（不裁剪工作集，不调用 `EmptyWorkingSet`）、已修改列表（等待
  写入磁盘的数据）、已提交内存、系统设置、服务和页面文件。只有这两个清除命令能被发送；其他命令
  在代码中被拒绝，并由测试验证。
- **效果：** *可用*内存几乎不变——这些缓存本来就算作可用。Windows 会在你使用过程中重建缓存，因此
  一段时间内应用和文件的打开速度可能稍慢。SnapBack 会把回收的缓存与关闭应用释放的内存分开显示，
  两者绝不相加。
- **权限：** 清除需要管理员权限和 `SeProfileSingleProcessPrivilege` 特权。SnapBack 本身仍以普通
  用户身份运行：仅为这一项操作，Windows 会显示 UAC 提示并启动一个短暂运行的辅助进程
  （`SnapBack.exe --deep-cleanup standby|low-priority`）。该辅助进程只接受这两个固定值，不读写
  任何文件，只通过退出代码报告结果。拒绝提示不会做任何更改。

## 安全第一

SnapBack 的基本原则是：**关闭错误的进程远比少关闭一些更糟糕**。详见 [docs/SAFETY.md](docs/SAFETY.md)。

- **只处理你自己会话中的你自己的应用。** 其他用户、其他会话的进程、服务、以管理员身份运行的进程、
  关键进程、受保护进程和 Windows 组件都是**受保护**的。没有任何设置可以解除保护。
- **默认拒绝（fail closed）。** 只要无法验证某个进程的任何安全相关信息（所有者、路径、权限提升、
  关键标志、保护级别），该进程就会被保护。
- **绝不单独信任 PID。** 每个进程都以 *PID + 创建时间* 识别。身份、可执行文件、会话、所有者和保护
  状态会**在执行操作所用的同一个句柄上**重新验证，因此被复用的 PID 永远不会被误伤。
- **三层独立防护：** 分类、在每次操作前重新检查实时进程的安全守卫，以及 Windows 层的句柄验证。
  界面中的错误也无法导致受保护的进程被关闭。
- **默认礼貌关闭，强制仅在请求时进行。** 窗口应用收到正常的关闭请求（`WM_CLOSE`），托盘应用通过
  不带强制标志的 Windows 重启管理器请求退出，控制台程序只有在没有无关程序共用控制台时才会收到
  Ctrl+C。强制结束需要单独确认，该确认只针对具体的进程实例，并在 5 分钟后失效。
- **配置文件和规则无法削弱上述任何一点。** “始终关闭”只会预先选中；受保护的进程始终受保护；WSL 和
  Docker 只会在发出警告后使用它们自己的命令停止。
- **日常使用无需管理员权限，没有驱动，没有服务。** 唯一以提升权限运行的代码路径是上文所述的可选
  深度内存清理辅助进程。

## 系统要求

- Windows 10（1809 及以上）或 Windows 11，x64 或 ARM64。
- 发布版本是自包含的——无需单独安装 .NET。

## 安装

从 [Releases](../../releases) 页面下载 `SnapBack-<版本>-win-x64.zip`（或 `win-arm64`），解压到任意
位置（例如 `%LOCALAPPDATA%\Programs\SnapBack`），然后运行 `SnapBack.exe`。可以用 `SHA256SUMS.txt`
校验下载文件。

没有安装程序，也不会在系统中注册任何内容。卸载时，先在设置中关闭“随 Windows 启动 SnapBack”（如果
启用过），通过托盘图标退出 SnapBack，然后删除程序文件夹和 `%LOCALAPPDATA%\SnapBack`。

## 使用方法

- **配置文件**选择器和**“配置文件”**——选择与哪个状态比较；创建、重命名、更新、编辑、删除配置
  文件，以及选择默认配置文件。
- **将当前状态设为基线**——当前正在运行的内容成为所选的配置文件。
- **基线之后新增 / 保留 / 受保护**——三个列表。点击列标题（“应用”“内存”“进程”“评估”）进行排序，
  再次点击可反向排序。内存按实际字节数排序。搜索框（Ctrl+F）可按应用名、可执行文件名或脚本名过滤。
  排序、搜索和刷新时都会保留你的选择。右键单击应用可设置规则。
- **返回基线…**（有多个配置文件时为**返回到“游戏”…**）——打开带有预期效果的预览；在你确认之前
  不会执行任何操作。
- **始终保留所选应用**——为所选应用添加“始终保留”规则。
- **内存**——内存详情、建议、内存随时间变化以及可选的深度内存清理。
- **历史**——每次操作的记录：配置文件、日期和时间、操作前 → 操作后的应用数 / 进程数 / 已用内存 /
  可用内存、应用释放的内存、已关闭的应用、强制结束的进程、是否使用了深度内存清理（以及它丢弃了
  多少缓存，单独显示）、已停止的环境和用时。历史记录保留最近 50 次操作（最多可设置为 500 次）。
- **设置**——语言、启动和通知区域、通知、关闭等待时间、是否预选“注意”类应用、规则、数据文件夹。

### 通知区域（托盘）

SnapBack 运行时，它的图标位于通知区域。图标的工具提示显示当前状态（*SnapBack · 干净 — 额外应用
7 个 · 约可回收 5.4 GB*），菜单提供“打开 SnapBack”“返回基线…”（打开窗口和常规预览——不会直接
从菜单关闭任何内容）、“选择配置文件”、**从当前状态更新“配置文件”…**、“刷新”和“退出”。

关闭窗口会把它隐藏到通知区域（第一次会有一条通知说明这一点）；在“设置 → 关闭窗口时”中可以让
关闭按钮改为退出程序。再次启动 `SnapBack.exe` 会显示正在运行的实例；`SnapBack.exe --quit` 会请求它
退出。

在后台，SnapBack 几乎什么都不做：窗口隐藏时每 15 分钟进行一次分析，在后台优先级的线程上运行，并
开启 Windows 的效率模式（EcoQoS）。两次分析之间不进行轮询；等待不消耗 CPU。

### 通知

通知是可选的（“设置 → 显示通知”），并且刻意保持稀少：当会话偏移为高，**并且**在内存逐渐紧张
（或预期效果为高）时返回配置文件可以回收至少 1 GB 的应用内存——最多每 6 小时一次，并且只有在偏移
回落之后才会再次通知；对于内存异常增长，每个应用实例只通知一次。每天最多三条，窗口打开时不会通知，
绝不会因为缓存内存而通知。Windows 的“请勿打扰”同样适用。

### 随 Windows 启动

“设置 → 启动”：

- **随 Windows 启动 SnapBack**——添加当前用户的 `Run` 启动项（`"…\SnapBack.exe" --autostart`），
  可在“Windows 设置 → 应用 → 启动”中看到。无需管理员权限，没有计划任务，没有服务。该启动项会跟随
  此设置，并会在你移动 SnapBack 后自动更正。
- **启动时最小化到通知区域**——登录时不会打开窗口。
- **启动后自动捕获基线**——每次登录时更新一次所选的配置文件（除非你另选，否则为默认配置文件）：
  至少等待 2 分钟，在 45 秒内没有新应用启动**并且** CPU 不再繁忙之后进行（均可配置，最长 10 分钟）。
  它绝不会关闭任何程序。

### 语言

内置 English、Русский 和简体中文。“设置 → 语言”可以选择“跟随系统”（跟随 Windows 显示语言；不支持
的语言会回退到英语）或固定的语言。更改会立即生效，无需重启。

## 命令行

`snapback-cli.exe` 与窗口共用同一引擎和全部安全检查。其输出为英文。

```text
snapback-cli status [--json]              配置文件、会话偏移、内存、预期效果、WSL/Docker
snapback-cli baseline create [--force]    将当前状态设为所选的配置文件
snapback-cli baseline show [--all] [--json]
snapback-cli list [--all] [--json]        基线之后启动的应用
snapback-cli preview [选择] [--json]      试运行：每个步骤和实时安全检查结果
snapback-cli restore [选择] [--yes]       请求所选应用关闭（绝不强制）
snapback-cli history [--json]
snapback-cli memory [--json]              已用内存与可重用缓存，并给出建议
snapback-cli profiles [--json]
snapback-cli profile create|update|rename|delete|default|use <名称> [<新名称>]
snapback-cli rules [--json]
snapback-cli rule keep|close|ask|clear <应用>
snapback-cli env [--json]                 WSL / Docker 状态（只读）

选择：--app <名称>（可重复）| --include-caution | --include-review
--profile <名称>：针对该配置文件执行 status/list/preview/restore（不会选中它）
```

CLI 有意**不能**强制结束任何程序，不执行深度内存清理，也不停止 WSL 或 Docker（窗口会先显示警告）。

## 局限性

- 分类部分依赖于已知的可执行文件名；未知应用根据其窗口判断（窗口应用总能询问你；没有窗口的应用
  需要人工确认）。
- 以管理员身份运行的应用永远不会被关闭（有意为之）。如果关闭了用户帐户控制（UAC），所有应用都会
  以提升的权限运行，SnapBack 会把它们显示为受保护。
- 同时忽略关闭请求和重启管理器的应用，只能由你手动关闭或通过明确的强制结束来关闭。
- 深度内存清理不会增加*可用*内存，它只是清空 Windows 本来就会重新利用的缓存。大多数情况下不需要。
- 内存列表大小来自 Windows 性能计数器；如果计数器被禁用，SnapBack 会改用系统缓存大小，并把未知
  数值显示为“—”。
- 会话偏移、预期效果和内存增长都是启发式判断。应用的私有内存加起来并不完全等于“已用内存”（共享
  内存、驱动程序、内核），因此其余部分显示为*系统及其他*。
- 内存历史只在 SnapBack 运行期间存在（不会保存），因此需要在后台运行几个小时后才能看出内存增长。
- 停止 Docker 需要 Docker Desktop 4.37 或更高版本（`docker desktop stop`）。安装在 WSL 发行版中的
  Docker Engine 会随 WSL 一起停止。WSL 的检测依据是 `vmmemWSL`（Windows 11）或 `vmmem`，以及 WSL 的
  辅助进程。
- 托盘图标需要资源管理器的任务栏；没有任务栏时，SnapBack 会改为显示它的窗口。

## 从源码构建

需要 [.NET SDK 10](https://dotnet.microsoft.com/download)（见 `global.json`）。

```powershell
git clone https://github.com/IT-Shelter-Labs/SnapBack-Rebootless.git
cd SnapBack-Rebootless
dotnet build SnapBack.sln -c Release
dotnet test SnapBack.sln -c Release
dotnet run --project src/SnapBack.App

# 自包含单文件构建
dotnet publish src/SnapBack.App -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -o publish
dotnet publish src/SnapBack.Cli -c Release -r win-x64 --self-contained -p:PublishSingleFile=true -o publish
```

与平台无关的核心及其 300 多个测试也可以在 Linux 和 macOS 上构建和运行
（`dotnet test tests/SnapBack.Core.Tests`）。CI 在 Windows 上构建、运行单元测试和集成测试、发布
应用，通过 UI 自动化在全部三种语言下操作真实界面，并检查托盘启动、自启动项、自动基线、空闲时的
CPU 和内存占用、激活已运行的实例、关闭到托盘以及 `--quit`。

翻译位于 `src/SnapBack.Core/Localization/Strings*.resx`（引擎文本）和
`src/SnapBack.App/Localization/Strings*.resx`（界面文本）。测试会验证每种语言都包含所有字符串，且
占位符一致。

## 数据与隐私

所有数据都保存在 `%LOCALAPPDATA%\SnapBack`（可用环境变量 `SNAPBACK_DATA_DIR` 覆盖）：
`settings.json`、`profiles.json`、`history.json`，以及 `logs\` 中的每日日志（保留 14 天）。内存历史
只保存在内存中。窗口标题和命令行只在界面中显示，绝不写入磁盘或日志。SnapBack 不进行任何网络连接。

## 常见问题

**它会关闭浏览器并丢失标签页吗？** 浏览器永远不会被预先选中。如果你选择了浏览器，它会收到与点击
✕ 相同的关闭请求，下次启动时照常恢复标签页。

**应用询问是否保存，而 SnapBack 显示“仍然打开”。** 这是有意的：SnapBack 在等待*你*。回答提示后
点击“重新检查”。

**深度内存清理后可用内存几乎没变——是坏了吗？** 不是。备用缓存本来就算作可用内存；清理只是把它
变成了“空闲”。这正是 SnapBack 从不把它当作必要操作推荐的原因。

**为什么 Docker Desktop 在“受保护”列表中？** 它的进程要用 Docker 自己的命令（“停止 Docker…”）
来停止，而绝不会被逐个关闭——那样可能损坏它的虚拟机，或让容器停在半途。

**关闭窗口后 SnapBack 仍在运行。** 这是通知区域模式；请从托盘图标的菜单中退出，或在“设置 → 关闭
窗口时”中选择“退出 SnapBack”。

**为什么深度内存清理需要管理员权限？** Windows 只允许提升权限的进程清除备用列表。SnapBack 只为这
一项操作请求权限，并通过一个别无他用的辅助进程完成。
